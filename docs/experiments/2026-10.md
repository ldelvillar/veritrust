# October 2026 experiments

## Judge-only screening (2026-10-01) — Ministral 14B, local candidate

`ml.evaluate_judge` with judge v6 on the same 95 single-Claim cases from
`eval_gold_extractor_v5.jsonl`. Mistral models through its API; `llama3.2` is the format
test from 2026-09-30 (Ollama, one field per Source), on the same cases:

|                  | `llama3.2` | `ministral-14b-2512` | `ministral-3:14b` (Ollama) | `mistral-small-2603` |
| ---------------- | ---------- | -------------------- | -------------------------- | -------------------- |
| judged           | 95         | 93                   | 95                         | 95                   |
| firm             | 71         | 71                   | 77                         | 68                   |
| correct          | 46 (65%)   | 65 (91.5%)           | **72 (93.5%)**             | 66 (97.1%)           |
| falsa→verdadera  | 22         | 4                    | **1**                      | 1                    |
| verdadera→falsa  | 3          | 2                    | 4                          | 1                    |
| s:c on true      | 3.8        | 22.2                 | 15.1                       | 27.8                 |
| s:c on false     | 1.8        | 0.18                 | **0.05**                   | 0.09                 |

- **`mistral-small-latest` is no longer a deployable candidate.** Today it is
  `mistral-small-2603` (Small 4), which weighs 119B in Ollama and does not fit in a
  16 GB VM; it is probably also the `mistral-small` behind the 0.58 of 2026-08-31. The
  API no longer serves Mistral Small 3.x (24B), so that family cannot be screened
  through the API.
- **`ministral-14b-2512` is the same weights as `ministral-3:14b` in Ollama** (~9 GB at
  Q4), the only deployable candidate the API lets us screen, and it separates almost as
  well as Small 4: with the same 71 firm verdicts as `llama3.2`, 4 falsa→verdadera
  instead of 22.
- Its 2 unjudged cases are `ValidationError`s: the API does not constrain output to the
  schema and the response fails validation. With Ollama the schema is enforced during
  generation.
- **Confirmed on Ollama**: `ministral-3:14b` with its default quantisation judges all 95
  (the schema is enforced during generation) and calls 1 false Claim of 77 firm
  verdicts `verdadera`. It takes ~11 GB loaded with `num_ctx` 8192; on a laptop with no
  usable GPU, ~70 s per case.
- The gold set is in-sample: what counts is the comparison between judges, not the
  93.5%.
- Cost: ~€0.07 per 95-case run with the Mistral API.

## Analysis Verdict from Claim Verdicts: `parcialmente falsa` (2026-10-12) — adopted

A fix to the Analysis Verdict, not to the judge. Averaging the falsehood score of the
Claims with Evidence lets a well-supported true Claim offset a false one. With Mistral
Small, the text "drinking diluted bleach kills the virus" + "a paracetamol overdose
causes liver damage" comes out **verdadera**: bleach false (0.67), paracetamol true
(0.17, four `supports`), average 0.42. Another text with refuted homeopathy and two true
Claims, the same. The single-Claim gold set cannot see it: with one Claim, the average
is that Claim.

The Analysis Verdict now follows from each Claim's Verdict (ADR-0002): false and true
Claims together give `parcialmente falsa`, with the Confidence of the strongest false
Claim. Single-Claim results do not change. In `evaluation.evaluate_pipeline`,
`parcialmente falsa` counts as a falsehood warning (positive), like `falsa`. A gold-set
row the extractor splits into two Claims can produce it.

Open: a multi-Claim set (15–20 texts with their key Claims and the expected Analysis
Verdict) to measure this rule and the extractor's trimming.
