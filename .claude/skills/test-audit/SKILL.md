# Test Audit

Gate every new or changed test. When auditing existing tests, remove low-value proof in coherent batches per production owner; never chase deletion counts.

## Authoring gate

Before adding a test, answer:

1. What observable behavior, invariant, or independent contract does it protect?
2. What credible regression makes it fail?
3. Why does existing proof miss it? Each contract has one primary owner at the strongest boundary; another layer needs a distinct transport or lifecycle risk. Extend parametrized tables and shared fixtures (`backend/tests/support/`, `frontend/e2e/fixtures.ts`) instead of copying setup.
4. Does it need an export, flag, wrapper, or injection hook that production never calls? Move the proof to the real boundary instead.

- Bug-fix tests must fail before the fix for the intended reason and pass after; say so when no baseline run is possible.
- One owner test covers a bug; never replay it at every layer it crosses.
- A behavior-preserving refactor must not break the test.

## Junk patterns

Reject, or remove when auditing:

- Assertion-free probes, self-comparisons, and expected values generated by the code under test.
- Copied inventories, manifests, or export lists; source or import greps.
- Call-shape and private-helper assertions that duplicate boundary proof.
- Duplicate contracts across unit, integration, and e2e.
- Test-only exports, globals, or wrappers; production paths called only by tests.
- Mocks that supply the behavior being asserted, such as a mocked LLM reply that already holds the verdict the test then "finds".
- Fixtures that fabricate state the owner should produce, such as Analysis status transitions or Run ordering, or that assert persistence the code never writes.
- Negative controls that pass on an unrelated guard; names that promise behavior the test never exercises.

## Retention bar

Keep independent contracts even when static or slow: API and schema shape (including the generated `api.d.ts` contract), config and `Settings` validation, migrations, auth and ownership, file and URL ingestion limits, billing and webhook handling, prompts' observable bytes, and Analysis lifecycle ordering (Retry vs Reanalyze, orphaned analyses). A source inspection is valid only when it is the cheapest independent guard of a user-facing contract and survives identifier-only renames.

A failing baseline test may be a product bug: reproduce it and repair the owner; never delete the test for it.

## Auditing existing tests

1. Read the full test, its production owner, callers, sibling tests, and the history of why it exists.
2. Record per candidate: name and location, the failure it detects, the stronger remaining proof (or why none is needed), and the risk.
3. Missing evidence means no deletion. Report candidates before editing; prefer a few high-confidence ones.
4. Delete obsolete production seams together with their tests, and prefer net-negative production LOC.

## Validation

Run the checks in `backend/AGENTS.md` and `frontend/AGENTS.md` for what you touched: the owner and sibling tests first, then ruff, mypy, and pytest at ≥80% coverage on the backend, or lint, typecheck, prettier, build, and e2e on the frontend. Removing tests can drop coverage below the gate; fix that by keeping the contract's owner test, not by suppression.

Report causes, retained contracts, remaining proof, and production versus test LOC changed. Commit or push only with task authority.
